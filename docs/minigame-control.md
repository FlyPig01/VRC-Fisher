# 小游戏控制

本文只定义 `catch_zone` 控制算法。历史实验见 [高频短脉冲实验](archive/minigame-high-frequency-pulse-2026-08-17.md)。

## 1. 游戏机制

- `moving_target` 在一维轨道内随机上下移动。
- 鼠标按住时，`catch_zone` 获得向上加速度；松开时获得向下加速度。
- 按下或松开只改变加速度，不会立即清除当前速度。
- 两个物体都有上下运动边界。
- 每轮开始时二者位于轨道中间且速度为零。
- 成功条件是 `moving_target` 完整位于 `catch_zone` 内。

控制器同时预测 `catch_zone` 和 `moving_target`。两者都使用最新坐标、真实识别间隔和局部运动数据，分别预测决策当前时刻与下一次反馈时刻；目标只使用最近有效画面估算出的短时带符号速度，不估算或保存目标加速度。

## 2. 坐标与有效输入

模型输出屏幕坐标，控制器立即转换为“向上为正”的中心坐标。后续位置、速度、加速度和边界判断只使用该坐标系。

一张控制画面必须同时满足：

- 包含 `catch_zone` 和 `moving_target`；
- 帧号和捕获时间晚于上一张控制画面；
- 捕获时间不晚于当前时刻；
- 帧龄不超过 `150 ms`；
- 目标高度不大于滑块高度。

第一次缺少任一组件时不生成新控制计划，也不刷新反馈计时；已有的有限计划可以继续执行。连续两次缺少组件、面板重定位或帧过期时释放左键并清空本轮运动历史。

## 3. 运动状态

### 3.1 参考单位

最近五张有效画面的 `catch_zone` 高度中位数作为参考高度。速度单位为“滑块高度/秒”，加速度单位为“滑块高度/秒²”，避免分辨率和 UI 缩放直接改变参数。速度是带符号的单个数：正值表示向上，负值表示向下，接近零表示没有明显位移；不另外维护运动方向枚举。

### 3.2 速度

保存最近三张有效画面。`catch_zone` 使用三张画面中最早和最晚的中心差除以真实捕获时间差，减少检测框抖动；`moving_target` 只使用最近两张画面，及时响应随机反向：

- 正数：向上；
- 负数：向下；
- 数值绝对值：运动速率。

### 3.3 加速度

连续三张画面的输入状态相同时，根据相邻两段速度变化测算对应加速度：

- `Released` 样本只接受负值；
- `Pressed` 样本只接受正值；
- 相邻间隔必须为 `15–200 ms`；
- 框高度变化不得超过参考高度的 `20%`；
- 加速度绝对值必须为 `0.1–40`。

每种状态保留最近五个有效样本，至少三个样本后使用中位数更新参数。

### 3.4 重置与持久化

新一轮、面板重定位或组件缺失时，清空坐标、速度、控制间隔和临时样本，但保留已经确认的按住/释放加速度。

正常停止时保存到：

```text
config/minigame-dynamics.json
```

下次启动将其作为初始值，并继续用新样本更新。

## 4. 完整容纳范围

控制器使用滑块中心判断目标是否能够完整位于滑块内部。

允许范围以目标中心为中点，上下各留出：

```text
(滑块高度 - 目标高度) / 2
```

目标比滑块高时不存在有效范围，控制器只能释放。

## 5. 轨迹候选

每次取得新的有效坐标后，控制器先按帧龄把截图时的滑块和目标状态推进到当前决策时刻，再将两者推进到下一次预计反馈时刻，比较两个时刻的相对距离和边界余量。截图产生到决策完成之间若发生鼠标按下或释放，执行器会提供真实转换时间；滑块按每段实际输入状态分别推进，不能把决策时的按键状态套用到整段截图延迟。

目标从截图时刻到当前时刻使用最近两帧测得的完整速度。从当前时刻到下一反馈时刻时，目标速度按“最近目标识别间隔 / 预计反馈周期”衰减，并限制在 `0.50–0.75`；较慢反馈不再把随机目标的旧方向完整外推。滑块仍使用完整速度、输入时间线和实测加速度。目标不使用输入状态，也不估算目标加速度。

每次决策会生成一段覆盖到下一次预计反馈的有限计划；后续新坐标可以重新计算并替换尚未结束的计划，这是正常的闭环控制行为。

当前低帧率补偿会主动预测下一次反馈前的下坠风险，并可在释放后安排再次按住。控制目标是以最少输入维持完整包含，计划生成后还会经过独立上冲限制。

### 5.1 当前为 Released

目标已经完整位于滑块内部时，默认保持释放。只有根据滑块与目标的相对速度、释放加速度和真实反馈间隔预测会越过边界，才比较立即按住方案。

目标位于滑块上方时，按住方案只追到允许范围下边界内侧的 `2%` 防抖余量。目标位于滑块下方时保持释放。若释放后会越过下边界，控制器仍可搜索一次安全的再次按下时刻。

### 5.2 当前为 Pressed

比较：

1. 目标已完整位于滑块内部且滑块正在向上：立即请求释放。
2. 目标已完整位于滑块内部且滑块正在向下：最早释放后不会跌破下边界就释放，否则只继续到足以制动的预测时刻。
3. 目标仍位于滑块上方：继续按住到恢复稳定包含所需的预测时刻。

新的有效坐标可以替换尚未结束的计划，并提前或延后释放、取消再次按下，或要求立即按下。控制器不会对已经按住的鼠标重复提交按下事件。

## 6. 选择规则

控制器首先按两个预测时刻的相对距离处理：允许范围上方直接释放；允许范围内部仍要检查下一反馈时刻是否会越界；允许范围下方才需要向上追赶。只有内部下坠风险或外部追赶需要比较方案时，每条候选轨迹才计算：

```text
下方余量 = 轨迹最低点 - 允许下界
上方余量 = 允许上界 - 轨迹最高点
双向余量 = min(下方余量, 上方余量)
```

双向余量为负表示轨迹会越界。

- 只有一条安全：选择安全轨迹。
- 两条都不安全：选择越界较小者。
- 两条都安全：选择双向余量较大者。
- 差值不超过滑块高度的 `2%`：保持当前输入状态，避免来回切换。

预测释放时刻通过搜索“释放后向上停止位置刚进入允许范围下边界内侧”的时间获得，不使用固定脉冲上限，也不追逐允许范围中点。

## 7. 包含优先与上冲限制

现有下坠逻辑先照常生成计划。控制器再根据当前状态计算不越过上边界的最晚松开时刻，最终松开时刻取原计划与上冲限制中较早的一项。原计划安全时不改变结果。

当前已经按住时会把剩余的 `60 ms` 最短按住时间计入检查；无法在上冲限制前松开时，立即请求释放，由执行器在满足剩余最短时间后松开。有按住加速度数据时，首次按住会先验证完整 `60 ms` 输入；计划内再次按住候选的整段预测轨迹只要超过上边界就会被取消。首次测量按住加速度时仍沿用原有 `90 ms` 初值，避免控制器因没有样本而永久无法开始学习。

新坐标仍会重新计算并提前或延后计划，但延后必须同时得到新的上冲限制允许。该实现没有修改实时参数、执行器、CPU/GPU 共用算法或日志结构。

## 8. 输入执行

- 新脉冲和计划内再次按下都至少保持 `60 ms`。
- 正常控制没有随机最长按住时间。
- 尚未测得按住加速度时，首次使用 `90 ms` 释放估计；它是初值，不是上限。
- 执行器可在两次有效坐标反馈之间按最新计划释放，并在确有必要时再次按下。
- 计划内释放到再次按下之间至少间隔 `20 ms`；再次按下必须能在计划期限前保留至少 `60 ms`。
- 计划期限取实际控制反馈间隔与当前性能调度间隔中较慢者，最长按 `150 ms` 规划；`60 ms` 最短按住保护优先于更短的计划期限。
- 每 `25 ms` 检查 VRChat 是否仍在前台。
- 正常反馈超时为预计反馈间隔的两倍再加 `40 ms`，并限制在 `180–350 ms`；超过期限强制释放。
- 停止、连续组件缺失、过期帧、推理失败或 VRChat 失去前台时立即请求释放。

松开后只接受捕获时间晚于实际松开时刻的新画面，避免旧画面立即触发下一次脉冲。

## 10. 现场验收

现场测试只判断以下结果：

- 目标在滑块外部时能够追赶且不过度上冲；
- 目标进入滑块后能够维持，不长期偏向下边界；
- 滑块向下时能够及时制动；
- 新画面能正确提前或延后释放计划；
- 看门狗只处理异常，不参与正常脉冲长度；
- 预测释放、实际释放和画面运动方向一致。

模型漏检或面板定位错误按 [BUG-023](bug.md#bug-023双模型识别质量不足) 单独处理，不作为控制算法结论。
