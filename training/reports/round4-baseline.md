# Round 4 训练前基线验证

日期：2026-08-14。此次只验证，不训练。评估集为新加入并人工审核的 `感叹号验证集`，共 75 张图片，其中 74 张有感叹号、1 张负样本。注意：这 74 张是同一个持续感叹号事件的不同动画阶段，不是 74 个独立事件。两套模型使用 Locator 输入尺寸 `960`，CUDA，`IoU=0.7`。

## 完整 PR 评估

Ultralytics 的完整 PR 指标使用 `conf=0.001`，用于计算 mAP，不是软件运行阈值。

| 模型 | Precision | Recall | mAP50 | mAP50-95 |
|---|---:|---:|---:|---:|
| `locator-best-init/best.pt` | 95.62% | 95.95% | 97.19% | 72.85% |
| `locator-round3/best.pt` | 93.07% | 97.30% | 98.18% | 72.63% |

Round 3 在低阈值下的 Recall 略高，但这不能代表软件默认运行时的效果。

## 事件级检查

在默认 `conf=0.35` 下，按视频时间顺序检查逐帧结果：

| 模型 | 命中动画阶段 | 未命中阶段 | 最大连续未命中 | 整个事件是否检测到 |
|---|---:|---:|---:|---:|
| best-init | 71/74 | 3 | 1 个采样帧（0.5 秒） | 是 |
| round3 | 66/74 | 8 | 2 个采样帧（1.0 秒） | 是 |

因此这里的 `3/74` 和 `8/74` 是动画阶段漏框，不是漏掉 3 次或 8 次钓鱼机会。Locator 的实际职责是：在感叹号持续显示期间至少检测到一次，然后触发确认点击。对这个职责，`best-init` 的事件级表现更稳定。逐帧 Recall 仍然用于发现某些缩放阶段的脆弱性，但不能单独决定是否重训。

当前 C# 软件默认 `ConfidenceThreshold=0.35`。以下结果按感叹号框 IoU >= 0.5 进行一对一匹配，统计 TP、FP、FN：

## 结论

1. 当前默认运行阈值下，`best-init` 比 Round 3 少漏掉 5 个感叹号，应该继续作为运行基线。
2. Round 3 的高 Precision 不能抵消 Recall 从 95.95% 降到 89.19%；对“感叹号出现后必须触发点击”的流程，漏检比少量误检更危险。
3. 预标注阶段的 60/74 候选框数量不能直接等同于上表正式结果。预标注调用了独立的 Python 后处理路径；正式运行使用 C# ONNX 后处理，后续需要统一两条路径的阈值和解码逻辑。
4. 当前不立即重训。先用 `best-init` 做完整视频人工验收，并确认 C# 运行链路的实际框和阈值。如果出现整个持续事件都无法触发，或出现长时间连续漏检，再补充新的训练录屏后进行 Locator Round 4。
